Blocker 1 — 018 will fail on its first statement

azure.extensions on psql-rewive-americana-prod is set to vector and nothing else. Migration 018 opens with CREATE EXTENSION citext and CREATE EXTENSION btree_gist. On Azure Flexible Server an extension that is not allowlisted cannot be created — IF NOT EXISTS does not help, because it does not exist and creation is refused.

Both are in the server's allowedValues and the parameter is dynamic — no restart, no downtime. It is a one-command fix, but it must happen before the migrate job runs. Every local test missed this because local PostgreSQL has no allowlist.

Blocker 2 — v91 returns 500 once 019 lands

The constraints in 019 are NOT VALID, which exempts existing rows but binds every new write immediately. POST /findings/{id}/re-alert in v91 sets status='open' without clearing the disposition, so it violates ck_findings_open_is_undecided on every call. That is the Park half of the loop.

The fix is in a1d8eaa but is not in any built image. Deploy the code before the migration, not after.

Blocker 3 — the migrate job is pinned to v91

Migrations are baked into the backend image and job-migrate-americana-prod currently runs rewive-backend:v91, which predates 018 and 019. Running it today applies nothing. The job image must be repointed to a build that contains them.

03 Backend integration

Behavior changes in 40ab097

Two route changes, both in app/routers/findings.py. Both were written to make existing behavior legal under 019, not to add features.

  1. POST /findings/{id}/re-alert — was SET status='open'; now also clears disposition, disposition_at and disposition_by. All three must move together: clearing status alone violates ck_findings_open_is_undecided, and clearing disposition alone violates ck_findings_decision_whole.
  2. POST /findings/{id}/disposition — abandon with an empty or missing reason now returns 400 before the write. Previously it returned 200 and stored a reasonless dismissal.

Ownership, grants, search_path, extensions

  • Runs as rewive_admin (PG_ADMIN_USER on the job), never rewive_app. Correct per doctrine.
  • Database americana. PG_SEARCH_PATH = fpa,shared,audit,rag,public, identical on the migrate job, the API and the worker — so type resolution for citext stays consistent.
  • Grants are explicit because 000's default privileges cover public only. 018 grants for shared; 019 grants for its own tables.
  • Extensions — see Blocker 1. gen_random_uuid() needs nothing; it is built into PostgreSQL 13+.
  • One structural note, not a blocker: because the CREATE EXTENSION statements are unqualified, citext installs into fpa. That is the same pattern vector already follows, and it works only while every connection shares the search path. Pinning extensions to a fixed schema would be more robust, but changing it now is a bigger decision than this deployment.

Behavior with existing Americana rows

All 8 added columns are nullable with no default, so PostgreSQL 11+ records them as metadata only — no table rewrite. All 6 constraints are NOT VALID, so no validation scan. On a Standard_B1ms server that distinction matters: neither operation reads the table.

Locks are brief ACCESS EXCLUSIVE for the DDL itself. Existing rows are neither read nor modified, and no row is rejected retroactively.

Rollback and recovery

There are no down migrations and I am not proposing any. The runner applies each file in its own transaction and records it only on success, so a failed migration rolls itself back and is not recorded — it simply retries on the next run once the cause is fixed. That is the primary recovery path.

SituationAction
018 or 019 fails mid-runNothing to undo. Fix the cause, re-run the job.
A constraint is rejecting legitimate writesALTER TABLE fpa_findings DROP CONSTRAINT <name>; — instant, metadata-only, fully reversible by re-adding it NOT VALID. This is the correct emergency lever.
New tables/columns unwantedLeave them. They are empty, unreferenced, and cost nothing. Do not drop columns — that is a rewrite and a data risk for no benefit.
CatastrophicPoint-in-time restore. Confirm the retention window before migrating, not after.

Can a constraint make v91 return 500?

Yes — two of them, and one fires on every call.

ck_findings_open_is_undecided makes POST /findings/{id}/re-alert fail unconditionally in v91. The route only accepts findings in status acknowledged, which is reachable only via disposition='acknowledge', so the disposition is always present and always left in place. Not intermittent — deterministic.

ck_findings_dismissal_has_reason makes POST /findings/{id}/disposition fail when abandon is sent without a reason, as an unhandled write error rather than a 400.

Both are fixed in a1d8eaa. This is the entire reason the deployment order below is not negotiable.

05 Safe deployment order

  1. Build a new backend image from a1d8eaa

    Call it v92. It contains both the route fixes and migrations 018/019. Nothing else in this sequence works without it.

  2. Allowlist the extensions

    az postgres flexible-server parameter set \
  -g rg-rewive-dedicated-americana -s psql-rewive-americana-prod \
  -n azure.extensions --value vector,citext,btree_gist

    Dynamic parameter — takes effect without a restart. Re-read it to confirm before continuing.

  3. Deploy API and worker to v92 — before any migration

    The v92 route code is fully backward-compatible with today's schema: clearing three already-existing nullable columns is legal without the constraints, and the abandon guard is pure Python. So v92 runs correctly on the pre-migration database.

    Watch replica-level restart counts, not just revision status.

  4. Run the preflight audit

    Section 04. Stop on any red condition.

  5. Repoint the migrate job to v92 and execute it

    The job has no MIGRATION_SET variable, so it runs the default numbered set and will pick up 018 then 019 in filename order.

  6. Verify, then stop

    Do not run VALIDATE CONSTRAINT in this window. It is a separate decision taken later with the audit counts in hand.

Why this order is the safe one. The dangerous window is any period where the new constraints exist and old code is running. v92 code is correct under both schemas; v91 code is broken under the new one. Code-first therefore has no failure window in either direction, and if the migration is delayed or abandoned, v92 keeps working indefinitely.

Migration-first would guarantee 500s on the Park re-alert path for the entire gap between the two steps.
